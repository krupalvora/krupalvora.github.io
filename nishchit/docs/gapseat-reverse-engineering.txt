Architecture
The phone does all the work: it fetches the chart, computes vacancy and hops, and shows results; Google services and a static site sit around it.
The dashed path is the one our PRD assumed: a server watching charts. IRCTC's edge refuses it, so either the watcher moves onto the phone or the data comes through a partnership.
Data sources and ingestion
All berth data comes from the JSON endpoints behind IRCTC's public Charts/Vacancy page; the page itself asks for train number, journey date and boarding station. Endpoint names are confirmed by public repos; request and response fields beyond those named below are not, and must be read off the page's own network calls in a browser.

Ingestion flow, per search (on device)
1.  Resolve train, date and boarding station from the user's input.
2.  Call trainComposition. If the chart isn't prepared, schedule a local retry at the expected chart time and stop.
3.  Call coachComposition for each coach in the selected classes, one at a time, with a 500 ms gap.
4.  Map every bsd[] segment onto station sequence numbers from the timetable.
5.  Compute vacancy and plans, then cache by train, date and chart stage.
Static data
• Station master and train timetables: bundled in the app, refreshed weekly from our CDN.
• Chart timing rules (20:00 previous day for 05:01 to 14:00 departures, 10 hours before for the rest): in remote config, not code. GapSeat's copy still says 8 hours, which shows the cost of hardcoding.

Planner output
Rules:
• Segments use half-open intervals [from_seq, to_seq) so a berth freed at a station can be taken at that same station.
• unknown is never treated as vacant.
• Snapshots are immutable; a second-chart fetch creates a new snapshot, so the two can be compared.
• No passenger names or PNRs are stored in this model.
Core algorithms
Three steps run on the device in under 50 ms for a full train: normalise segments, find plans, rank them.
1. Normalise segments
• Map each bsd[] entry to [from_seq, to_seq) using the timetable order.
• Merge only adjacent vacant segments of the same berth; gaps stay gaps.
• Drop segments that end before the user's origin or start after the destination.
2. Find plans
1.  Full journey: any berth with one vacant interval covering [origin, destination).
2.  Seat hopping: greedy interval cover; from the current station, take the vacant interval reaching furthest, repeat. This gives the minimum number of legs.
3.  Partial: when the destination is unreachable, return the plan reaching the furthest station, with km covered.
legs = []; c = origin
while c < dest:
    best = max(vacant segments with from_seq <= c < to_seq, key = to_seq)
    if best is None: return partial(legs, c)
    legs.append(best.clip(c, dest)); c = best.to_seq
return legs
3. Rank (GapSeat publishes no ranking; this order follows the public IRCTC_Chart_vacant tool, then adds ours)
1.  Km covered (verified from the timetable).
2.  Fewer legs.
3.  Lower berths first; side berths last on legs over 6 hours.
4.  Same or adjacent coach at each switch.
Test fixtures: capture 20 real snapshots per class (SL, 3A, 2A, CC) and assert plan output; field meanings may change without notice.

Clients
One Flutter codebase covers Android and iOS (GapSeat has no iOS app); the website is a static SEO layer that funnels installs.
Mobile app (Flutter)
• Screens: search (PNR or train or two cities), results by coach, plan detail, watched trips, settings.
• Background: Android WorkManager and iOS BGTaskScheduler wake the app near chart time, fetch, and raise a local notification. iOS gives no exact timing, so iOS users also get a "check now" prompt at chart time.
• Storage: SQLite for snapshots and watched trips; purge 7 days after travel.
• Ads: none in v1; GapSeat's ads compete with a time-critical task.
• Telemetry: Firebase Crashlytics and Analytics, with no PNR or search text in events.
Website (Next.js, static export)
• One page per popular train and route, generated from the timetable, plus Hindi and regional versions; this mirrors GapSeat's main acquisition channel.
• Each page explains chart timing for that train and links to the app.
• No live chart lookups on the web in v1: a browser tool would need either cross-origin access to IRCTC or a server proxy, and a cloud proxy hits the 403 block.

Security, privacy and legal
Using IRCTC's chart data is a grey zone: not clearly illegal, not clearly permitted. India has no scraping statute, so the risk turns on how the data is accessed, what is taken and how it is used (LegalKart). This is not legal advice; get a written opinion before launch.

Technical blocks

Copyright Act 1957
Facts aren't owned; a compilation needs originality (Eastern Book Co. v. D.B. Modak)
Berth status is factual: low risk. Don't copy IRCTC's UI, logo or name

Governs personal data; public availability is not a blanket exemption
Chart berth data has no names; PNR handling brings the Act in
Railways Act s.143
Up to 3 years in jail for unauthorised business of procuring and supplying tickets (CourtBook); the Supreme Court called it a social crime in 2025 (Drishti)
Never book on users' behalf without authorised agent status
Risk tiers
• Lower: user-initiated, on-device, throttled reads of the public page; cached; no login; nothing bypassed; source credited; no resale. This is GapSeat's apparent pattern.
• Higher: server-side crawling of every train, storing vacancy history at scale, selling the data or an API, retrying through 403s.
• Off-limits: evading blocks (proxy pools, IP rotation, CAPTCHA solving), booking for users, IRCTC branding.
Our "should I wait?" vacancy history needs bulk collection, so it sits in the higher tier: get written permission from IRCTC or CRIS before building it.
Security and privacy requirements
• Never ask for IRCTC credentials or OTPs.
• Keep PNRs on the device; if one must reach our server, take explicit consent, encrypt it and purge it 7 days after travel.
• Keep the Play data safety form consistent with the privacy policy. GapSeat's form says no data is collected while its policy lists IP, location and search queries: a Play policy risk we shouldn't copy.
• Show "not affiliated with IRCTC or Indian Railways; a plan is not a ticket" on every results screen.
